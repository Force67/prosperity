// ---------------------------------------------------------------------------
// SOLVED: THE BLACK SCREEN WAS SPI_PS_INPUT_CNTL
// ---------------------------------------------------------------------------
// A PS names an input SLOT; SPI_PS_INPUT_CNTL_<slot>.OFFSET names which VS
// parameter export that slot reads, and it is NOT the identity. The UI shader
// ps=0x2000873c00 reports numinterp=2 with slot0 -> param0, slot1 -> param3.
// We assumed the identity, so slot1 read param1 -- the clip position -- as a
// texture coordinate and the vertex colour as its scale. Every UI quad sampled
// texel (0,0) and multiplied it by zero.
//
// Honouring the register is now the default (DELTA_GPU_PSCNTL_APPLY=0 goes
// back). Isaac, Undertale and Doom64 present the same frame either way; the old
// "it makes P.T. worse" note no longer reproduces -- P.T. presents black at
// frames 200 and 900 with the mapping on or off.
//
// PROBES ADDED THIS SESSION. +DELTA_GPU_DRAWRT takes a PIXEL SHADER address as
// well as a target (a deferred light lands on the same address as the base
// pass, and only the shader separates them); with DRAWRT=1 a DRAWRT_BUSY
// threshold latches onto the first frame that reaches it and prints the whole
// graph, so no frame number has to be guessed. Each draw now reports its
// instance count and the CONTENTS of every raw buffer it reads, which is the
// only way to see a shader that fetches its own vertices.
// +DELTA_GPU_RTSTAT_MAX raises the 32-target scoring cap (this title has 44).
// +DELTA_GPU_PROBE_PS=<hex ps address> restricts PSWHITE/PSTEX/PSATTR/PSVGPR/
// PSREACH to ONE shader, so a probe finally runs inside a complete frame.
// Every one of them used to rewrite every shader's colour, which left
// isolation (ONLY_PS) as the only way to read a single pass -- and isolating a
// DEFERRED pass drops the G-buffer it samples, so it answers a different
// question than the one being asked. This is the tool the light shader needs:
// +DELTA_GPU_PROBE_PS=0x20010c4000 +DELTA_GPU_PSTEX=13 exports binding 12's
// texel (the IES profile the final multiply uses) from the light draws alone,
// with the rest of the frame intact.
//
// How it was found, because the sequence generalises:
//   +DELTA_GPU_PSWHITE=1     -> whole screen white: geometry and raster are fine
//   +DELTA_GPU_PSTEX=1       -> black: the sample reads zero
//   +DELTA_GPU_FORCEWHITE=1 with PSTEX -> still black: not the texture DATA
//   +DELTA_GPU_DEBUGUV=1     -> black: the COORDINATE is zero, so the varying is
//   +DELTA_GPU_PSINCNTL=1    -> names the shaders whose mapping is not identity
//   +DELTA_GPU_PSREACH=1     -> white where a fragment reached no colour export
// and +DELTA_GPU_ONLYDRAW=<n> isolates one draw while all of those are on.

// Three things had to go first:
//   - A DEVICE FAULT, every time, ~35 s in. The heuristic path bound a colour
//     attachment unconditionally, so a depth-only pass opened a region on an RT
//     keyed at address 0 whose geometry followed whichever draw touched it
//     last, and a 1020x1020 shadow pass then rendered into a 1470x827
//     attachment. Validation named it: VUID-VkRenderingInfo-pNext-06079/06080.
//     A draw with no colour target now takes no colour region.
//   - THE RAW-BUFFER RING. Each staged resource reserved a whole 1 MiB window
//     whatever its size; the world binds three a draw totalling ~50 KB, so a
//     frame ran out after ~85 draws of several thousand and the rest were
//     declined -- silently, because a declined draw simply never appears.
//   - THE STAGE CACHE keyed on the exact length, so the shared 200k-vertex
//     buffer each draw reaches a little further into missed every time and
//     re-copied ~2.4 MB per draw.
// Together: 3016 declines a frame -> 5, ring declines 251255 -> 0, the
// raw-buffer ring from pegged at 256 MiB to 84 MiB, and no device fault in
// 300 s with validation on.
//
// ---------------------------------------------------------------------------
// THE POST CHAIN WAS BEING FED ZEROS -- FIXED
// ---------------------------------------------------------------------------
// UE4 does its post-processing in COMPUTE, and a compute shader reads guest
// memory. Draws only ever render into a VkImage, so the guest bytes under a
// render target stay stale -- the bridge (StageCsRangeFromRt) exists to copy
// the image into the staged range instead. It refused this title's scene
// target on both of its checks:
//   image 1680x945 4B vs cs 1680x948 pitch=1792 dfmt=6 elem=4/16B
// -- the extent because a target's IMAGE is sized from CB_COLOR's pitch/slice
// while the CS descriptor carries the surface's own height, and the element
// because StageCsImage unpacks R11G11B10F into four floats a texel and no
// image<->buffer copy converts. So every dispatch fell back to guest memory,
// read zeros, and the whole chain after the base pass was black. The bridge
// now copies the overlap and converts through a host scratch.
// Measured over the same cutscene: 0x2013800000 (scene colour after AA)
// nz 174 -> 11531 of 16384, the 840x474 bloom 0 -> 11178, and the frame graph
// downstream carries real content for the first time.
//
// ---------------------------------------------------------------------------
// AND THE DEPTH BUFFER WAS 256x256 -- FIXED
// ---------------------------------------------------------------------------
// Colour targets have been sized from CB_COLORn_PITCH rather than the screen
// scissor since the 164-draws-into-256x256 bug; DEPTH never got the same
// treatment. This title opens a 256x256 screen scissor over its 1792x960 Z
// surface, so the depth image was built 256x256 while every colour attachment
// beside it was 1792x960 -- and everything downstream that reads scene depth
// read a corner of the frame. The compute bridge said so on every frame:
//   cs reads live depth target 0x200b800000 shape mismatch:
//     image 256x256 4B vs cs 1680x948 ... -> falling back to guest memory
// i.e. every compute pass that samples scene depth or stencil (SSAO, fog,
// reflections) was reading the zeroed guest bytes, and the deferred lights
// reconstructed world position from a 256x256 Z. GetDepthRT now takes
// RtSurfaceExtent(depth_w/h, ...) exactly as the colour path does -- which
// only ever GROWS the image to the surface, so a genuinely half-resolution Z
// bound to a full-resolution pass still keeps the drawn extent. Measured over
// the same cutscene: scene depth and stencil go from guest-fallback on every
// frame to 198 staged-from-RT against 2 (the two before the target exists),
// and the lit scene stops being flat per-polygon slabs and starts varying per
// pixel. Isaac and Doom64 unchanged.
//
// ---------------------------------------------------------------------------
// SOLVED: THE COLOUR-GRADING LUT WAS A GEOMETRY-SHADER PASS
// ---------------------------------------------------------------------------
// The LUT (rt=0x200e680000, 32x32x32, vs=0x200084ac00) is drawn by an ES -> GS
// pipeline: ES 0x200084ad00 stores 9 dwords per vertex to the ESGS ring, GS
// 0x2000879000 re-emits each triangle with the slice as the layer, and the VS
// slot holds the copy shader. Its "raw vertex buffer" with base-high 0x3020
// is the GSVS ring descriptor out of the global resource table, which is why
// no guest code or DMA ever wrote it. Ring layouts, as translated: ES stores
// component c at byte 4c; GS reads vertex k component c at k*4 + c*0x100
// (the vertex offset VGPRs are ring lanes); GS writes vertex k component c at
// dword c*maxvert + k; the copy shader reads component c at c*maxvert*64.
//
// ---------------------------------------------------------------------------
// THE LIGHTS: THE GATE IS BACK IN PLAY, AND PSREACH CANNOT SEE IT
// ---------------------------------------------------------------------------
// ps=0x20010c4000 is 2843 instructions and opens with a gate:
//   0019  image_sample_lz v[0:3], v10, s[12:19], s[32:35]  ; GBufferB
//   001f  image_load      v14,   v4,  s[20:27] dmask:0x1   ; lighting channels
//   002b  v_and_b32 v42, 15, v3          ; v42 = the SHADING MODEL id
//   002c  v_cmp_lt_u32 s[12:13], 0, v42  ; shading model > 0 ?
//   002f  v_and_b32 v14, s38, v14        ; s38 = the light's channel mask
//   0031  s_and_b64 vcc, s[12:13], vcc   ; BOTH
//   0033  s_cbranch_execz pc+3678 -> 0e92
// The earlier reading of this -- "PSREACH says no fragment misses its export,
// so the gate is taken by nobody" -- is WRONG BY CONSTRUCTION. 0e92 is not
// s_endpgm: it falls through to the export at 0e9d, and v7/v8/v9/v13 are
// zeroed at 0002/0023/0024/0025 precisely so a rejected lane exports zero. A
// gate-failing lane still reaches a colour export, so PSREACH is blind to this
// branch. Read the gate's inputs directly instead.
//
// And the binding map used to read it was wrong too. The recompiler numbers a
// shader's textures in PROGRAM order, not by their slot in the T# table, so
// for this shader:
//   t0  = 0x2010800000  GBufferB      (the gate's shading-model input)
//   t1  = 0x202b800000  dfmt=2 nfmt=4, i.e. R16_UINT -- the LIGHTING CHANNELS
//                       surface the gate masks, NOT 0x200e000000 and not a
//                       "shadow buffer"
//   t12 = 0x2001c80000  256x256 RGBA16 -- the IES profile, sampled last at
//                       0e84 with spherical coordinates, and the final
//                       multiply: exp = cb[0x21d] * IES * (diffuse+specular).
// A single zero in t1 or t12 blacks the whole light out.
//
// THE LIGHTS STILL EXPORT ZERO. The "flat uniform blue over the road-and-bus
// silhouette" that a full frame shows in 0x2012800000 is NOT the lighting: it
// is the heuristic quad renderer. With the shader filter fixed (below) so that
// only the light shader's own draws survive, its target reads nz=0.
//
// **DELTA_GPU_ONLY_PS USED NOT TO ISOLATE A PASS -- FIXED.** The filter lived
// inside DrawRecomp, and the caller only gets there when `d.recomp` exists
// (vk_draw.cc: `kRecompPath && d.recomp && DrawRecomp(...)`). A draw whose
// shader never recompiled has no `d.recomp`, skipped the filter entirely and
// was drawn by the HEURISTIC quad renderer, which no SPIR-V probe can touch.
// The tell was two probes that change different things
// (+DELTA_GPU_DEBUGUV=1 and +DELTA_GPU_PSATTR=1) agreeing to the BYTE --
// exactly (128,128,255) at every covered pixel from both. It is asked at the
// renderer's entry point now, before either path.
// Note what isolation costs for a DEFERRED pass, though: dropping every other
// draw also drops the G-buffer the light samples, so "isolated and black" says
// the shader exports zero, not why.
//
// So the multiply chain is where to look next, and its last two terms are the
// cheap ones: the export is
//   0e96  v_mul_f32 v0, s0, v7      ; s0 = View cbuffer dword 0x21d, a SCALAR
//   0e8e  v_mul_f32 v7, v0, v2      ; v0 = the t12 IES sample at 0e84
// NEITHER IS THE ZERO, and the probe that says so is the one worth reusing:
// +DELTA_GPU_PROBE_PS=0x20010c4000 aims a probe at that shader alone and
// leaves the rest of the frame intact, which is what makes a DEFERRED pass
// readable at all.
//   - s0: +DELTA_GPU_CBSTAGED=0x2000e65800 dumps the staged View block
//     (bind=1, 4192 bytes) and dword 0x21d reads 1.0.
//   - the IES sample: PROBE_PS with +DELTA_GPU_PSTEX=13 exports binding 12's
//     texel from the light draws only, and it comes back BRIGHT over large
//     areas. So the light volumes rasterize plenty of pixels and the final
//     multiplier is not zero either.
//   - PROBE_PS with +DELTA_GPU_PSVGPR=8 exports v7/v8/v9 -- the product just
//     before the s0 scale -- and the target comes back INDISTINGUISHABLE from
//     the unprobed one: mean R=83.4 G=0.1 B=0.0 over 65% coverage against
//     R=83.5 G=0.0 B=0.0 for the same shader unprobed. The probe changes
//     nothing, so v7/v8/v9 are ~zero: the accumulated lighting IS the zero.
//     DO NOT READ THESE IMAGES BY EYE. The red they are full of is the BASE
//     PASS's MRT0, not the light draws, and it looks identical either way --
//     comparing channel MEANS against an unprobed run of the same shader is
//     what separates them, and it overturned a "the lights are red-dominant"
//     reading taken from the pictures alone. The PSTEX probe is the control:
//     it moves the means a long way (R=119/G=1.4/B=0, R=0.7/G=0.9/B=12.2 on
//     other frames), which is how you know a probe reached the pixels.
// So of
//   0df3-0df8  v29=v4*v10  v31=v42*v6  v30=v44*v7
//              v16=v11*v10 v28=v12*v6  v15=v13*v7
//   0e79-0e88  R=v29+v16   G=v31+v28   B=v30+v15
// all three terms come back at zero, with the gate, the IES sample, the light
// colour and s0 all measured live -- so the fault is between the gate at 0x33
// and the combine at 0e79, in the accumulation itself.
//
// AND 0x2012800000 IS NOT HOLDING A COLOUR AT ALL. Read the RAW texels
// (+DELTA_GPU_RTDUMP_RAW=1) rather than the PPM and the picture changes
// completely:
//   row 500, x=100.. : 00000387 00000381 00000378 0000036d 00000362 00000356
//                      0000034b 00000340 00000329 00000327 00000340 0000034e
// Only the LOW 11 BITS are ever set -- 192 of 32459 sampled texels have
// anything above bit 10 -- and the values walk smoothly. In B10G11R11 that is
// R sweeping 0.25..0.6 with G and B exactly zero: a smooth SINGLE-CHANNEL
// GRADIENT, which is the shape of a depth/AO/luminance buffer, not of UE4
// SceneColor. It is there at frame end AND with the frame cut off at draw 2500
// (+DELTA_GPU_MAXDRAW=2500, i.e. after the base pass and the lights but before
// the whole post chain), so it is not a later pass reusing the address.
//
// The address IS SceneColor, though -- that part of the old map is right. The
// main base pass is 634 draws of `rt=0x2012800000 1470x827 mrt=6`, and its six
// attachments are
//   mrt0 0x2012800000 fmt=6  ntype=7  (B10G11R11)  SceneColor
//   mrt1 0x2010000000 fmt=9  ntype=0  (2_10_10_10) GBufferA, normals
//   mrt2 0x2010800000 fmt=10 ntype=0  (8888)       GBufferB
//   mrt3 0x2011000000 fmt=10 ntype=6  (8888 SRGB)  GBufferC, base colour
//   mrt4 0x2011800000 / mrt5 0x2012000000          GBufferD/E
// (the six-target pass at 0x2018000000 is a separate 256x256 capture, RGBA16F).
//
// AND IT IS NOT A WRITE-MASK DEFECT. +DELTA_GPU_MASKTRACE=1 with
// MASKTRACE_RT=0x2012800000 reports the same thing on every base-pass draw:
//   TARGET_MASK=0xffffff SHADER_MASK=0xffffff eff0=0xf COLOR_CONTROL=0xcc0010
//   mode=1 BLEND0=0x0 en=0 psMrtMask=0x3f recomp=ok
// -- a full RGBA mask on attachment 0, no blending, and the recompiler
// emitting all six outputs. So whatever leaves G and B at zero is upstream of
// the attachment state.
//
// AND THE WRITE PATH IS NOT AT FAULT -- settled by the one test with no
// coverage question in it. +DELTA_GPU_PSWHITE=1 with no PROBE_PS forces EVERY
// shader white; the raw texels then read
//   84210420  (22938 of 32459 samples carry bits above bit 10)
// i.e. all three channels populated, at the magnitude repeated additive white
// writes should give. So our B10G11R11 export and attachment path writes RGB
// correctly, and the single-channel gradient the target normally holds is what
// the title's own shaders put there. That closes the renderer as a suspect and
// sends the question back to what the base pass computes.
//
// A CAUTION FOR THE NEXT ATTEMPT, learned twice over. Sampling every 37th
// pixel of the PPM made this gradient read as red NOISE, and a PROBE_PS run
// covering only 245 of the pass's 634 draws made a minority value look like
// the whole target's. READ THE RAW TEXELS, and check what share of a pass a
// probe actually covers before attributing the target's content to it -- or
// use a probe with no coverage question at all, as above.
//
// THE LIGHT COLOUR IS NOT THE ZERO EITHER. v10/v6/v7 are that colour:
//   0dd3  s_buffer_load_dwordx4 s[12:15], s[4:7], 0x10   ; b5 dwords 16..19
//   0dd8  v2=s12*v21  v0=s13*v21  v1=s14*v21
//   0ddb  v10=v23*v2  v6=v23*v0   v7=v23*v1
// and +DELTA_GPU_CBSTAGED=0x2000e65800 shows bind=5 (0x2024d72c00, 1024 bytes)
// reading `@0x40: 4.43962 3.01914 2.06271 8` -- a real warm-white RGB, all
// three channels live. s4 = b5 dword 0x17 = 1.0, so v11/v12/v13 are just
// v5/v24/v41.
//
// THE LIGHT MASK IS NOT THE BLOCKER (measured properly -- see the end of this
// section). What follows maps the gate, which is still the right code to know.
// The real gate is not the one at 0x33. At 0x00c6 the shader builds UE4's
// light attenuation mask and skips the ENTIRE lighting body if it is zero:
//   00bc  v5 = clamp(1.0 - v6)          ; v6 = d^2/r^2
//   00c0  v5 = log2(v5)
//   00c3  v5 = s28 * v5                 ; FalloffExponent
//   00c5  v5 = exp2(v5)                 ; radial falloff
//   00bf  v4 = v17 - s63                ; cos(spot) - SpotAngles.x
//   00c1  v4 = clamp(s64 * v4)          ; * SpotAngles.y, saturate
//   00c4  v4 = v4 * v4
//   00c6  v21 = v4 * v5                 ; LightMask
//   00c7  v_cmp_lt_f32 vcc, 0, v21
//   00c9  s_cbranch_execz pc+3399 -> 0e11   <-- skips 0xca..0e10 entirely
// and v21 is also the common multiplier on all three light-colour channels at
// 0dd8-0dda, so a zero there blacks the light twice over.
//
// THIS SHADER'S OWN CONSTANTS ARE FINE. +DELTA_GPU_DRAWRT=0x20010c4000 filters
// by PIXEL shader (CBSTAGED filters by the vertex one, which every light draw
// shares) and prints its b5:
//   @0x40: 54.5606 52.7761 43.8372 3 | 1.5e-07 -1.3e-07 1 1
//          | -0.951057 0.309017 -3.3e-07 0 | -2 1 0 0
//   dw16-18 colour (bright)   dw24-26 a unit direction   dw28/29 = -2, 1
// so s63 = -2 and s64 = 1.0, UE4's point-light SpotAngles sentinel, on the
// draws that actually run this shader.
//
// AND THAT RETRACTS THE "s64 <= 0" BISECTION. It read the R FIELD of the scene
// target -- which is exactly the field the base pass writes -- so its 163157
// "nonzero" texels at AT=0xc0 were the base pass, not the probe, and the two
// captures landed on frames with completely different base-pass content
// (AT=0xc0 gave R/G/B 163157/680/680, AT=0xc6 gave 0/1815/0). Neither the
// comparison nor the conclusion drawn from it is sound.
//
// HOW TO TAKE IT PROPERLY: the base pass writes the R field ONLY (raw texels,
// above). So choose the PSVGPR base register so the value of interest lands in
// G or B, which nothing else touches. For v4 at 0xc6 that is PSVGPR=3
// (first=2): out.r=v2, out.g=v3, out.b=v4, and the B field is then the probe's
// alone. Same trick for any other term.
//
// TAKEN THAT WAY, THE MASK IS ALIVE. PSVGPR=3 + PSVGPR_AT=0xc6 reports
//   B field = v4 (the spot factor)  nonzero in 78323 of 245760 texels
// with G and R at 78324 -- the probe covering ~32% of the frame, the light
// volumes' footprint, and every field it wrote coming back non-zero. So v4 is
// NOT zero, the gate at 0x00c7 is NOT masking the lights off, and the whole
// "one constant kills the lighting" line is dead.
//
// WHICH MEANS EVERY EARLIER READING OF THIS SHADER TAKEN THROUGH THE R FIELD
// IS SUSPECT. Retake them with the value in B. The instrument is sound now;
// the readings taken before it was are not.
//
// RETAKEN, AND THIS IS WHERE THE LIGHT GOES. PSVGPR=8 + PSVGPR_AT=0xe91 -- the
// four lighting products, just after 0e8e-0e91 build them -- puts v8 in G and
// v9 in B, both clean:
//   mask, v4 @0xc6 : 78323 texels    <- the light's whole footprint
//   green, v8 @0xe91:  8268 texels   <- ~10% of it
//   blue,  v9 @0xe91:   342 texels   <- ~0.4% of it
// So the lights DO pass their attenuation gate and then produce nothing on all
// but a few percent of that footprint. The collapse is between 0xc6 and 0xe91
// -- inside the lighting body itself, not in the gate, not in the constants,
// not in the final multiplies. That is the range to bisect, with the value in
// G or B every time.
//
// BOTH MASK TERMS ARE ALIVE, measured together in ONE frame so the counts are
// comparable (PSVGPR=4 @0xc6 puts v4 in G and v5 in B, both clean):
//   G = v4, spot factor     3852 texels
//   B = v5, radial falloff  2921 texels   -- 76% of the same footprint
// so v21 = v4*v5 is non-zero over three quarters of where the lights land.
// COMPARE COUNTS ONLY WITHIN A FRAME: the footprint itself swings by an order
// of magnitude between frames of this cutscene (78323 in one, 3852 in
// another), so a count from one run means nothing against a count from
// another. Every cross-run comparison this file used to make was wrong for
// exactly that reason.
//
// FIRST BISECTION STEP INTO THE BODY. 0cea is `v_mov_b32 v51, 4` -- a known
// constant, so capturing it is a pure REACHABILITY test: PSVGPR=50 @0xcea puts
// v51 in B, and a non-zero B means that pc executed for that pixel.
//   B = v51  115 texels
// Small, but taken on a frame whose footprint was not measured in the same
// capture, so it bounds nothing on its own. Take it again PAIRED with a
// footprint in another clean field (there is no free register adjacent to v51,
// so either move the probe to a pc where one is, or accept two captures at the
// same PSVGPR_AT on the same frame index and compare only their B fields).
// The reachability idea is the right one: bisect 0xc6..0xe91 by capturing a
// known constant at each candidate pc and asking which of them execute.
//
//   0081  s_buffer_load_dword s63, s[4:7], 0x1c   ; b5 dword 28
//   0082  s_buffer_load_dword s64, s[4:7], 0x1d   ; b5 dword 29
// and the STAGED b5 (+DELTA_GPU_CBSTAGED=0x2000e65800, bind=5, 1024 bytes)
// holds exactly what UE4 writes for a point light:
//   @0x40: 4.43962 3.01914 2.06271 8 ... 50 -2 1 0 0
//          ^dw16 colour RGB              ^dw27 ^dw28=-2 ^dw29=1
// SpotAngles = (-2, 1) is UE4's point-light sentinel, chosen so that
// saturate((cos + 2) * 1) is 1 for every direction. With s64 = 1 confirmed for
// this shader's own draws, a zero mask needs v17 <= -2 -- a dot product out of
// range, i.e. the light vector or the reconstructed world position, not the
// constants. That is the thread to pull, with the clean B-field readout.
//
// THE MODULE IS RIGHT TOO. +DELTA_GPU_SPVDUMP_ADDR=0x20010c4000 emits it, and
// spirv-dis shows exactly the right slots:
//   %1903 = OpAccessChain %_ptr_Uniform_uint %cbuf5 %uint_0 %uint_7 %uint_0
//           -> sgpr[63]        ; b5 dword 28
//   %1907 = OpAccessChain %_ptr_Uniform_uint %cbuf5 %uint_0 %uint_7 %uint_1
//           -> sgpr[64]        ; b5 dword 29
// So the decode, the plan, the lowering and the descriptor all agree.
//
// WHICH LEAVES A QUESTION ABOUT THE READING ITSELF. The "-2, 1" above came
// from +DELTA_GPU_CBSTAGED=0x2000e65800, which filters on the VERTEX shader --
// and that VS is shared by every light draw in the frame, whose b5 buffers are
// NOT the same: the dumps show bind=5 at 0x2024d72c00 with 1024 bytes on one
// draw and at 0x2024cfe700 with 144 bytes on another. The staged bytes read as
// SpotAngles=(-2,1) belong to whichever draw that line came from, which is not
// necessarily one running ps=0x20010c4000. So s64 <= 0 is measured and solid;
// "the guest staged 1.0 there" is NOT, until CBSTAGED is filtered by the PIXEL
// shader (or the draw index is matched) and dwords 28/29 of THIS draw's b5 are
// read. Do that first: it decides whether this is our defect or the title
// legitimately masking those lights off, and the two lead in opposite
// directions.
//
// Everything else obvious has been checked and is fine:
//   - s[4:7] is not reused. It is written only at 0dfc and 0e66, both AFTER
//     the loads at 0081/0082, so the "same SGPR, two descriptors" hazard
//     PlanCbufs keys around does not apply here.
//   - the two instructions are the same form. c21f851c (s63, offset 0x1c) and
//     c220051d (s64, offset 0x1d) both decode IMM=1, SBASE=2 -> s[4:7].
//   - the ring slot holds the bytes: CBSTAGED prints -2 and 1 at dwords 28/29.
//   - the descriptor range is kCbufWindow for every binding and the copy is
//     min(cb.size, kCbufWindow) with cb.size 144..1024, so byte 116 is inside.
//   - CbufDword(29) lowers to AccessChain(vec4 7, component 1), which is right.
// So dump the module (+DELTA_GPU_SPVDUMP_ADDR=0x20010c4000, spirv-dis it) and
// compare what it emits for offset 0x1d against 0x10 -- the colour load from
// the same buffer works, so the two differ somewhere between the decode and
// the AccessChain. Worth checking DecodeSmrdOffset on an ODD dword offset
// specifically: 0x1c works into s63 and 0x1d does not, and they are adjacent.
//
// Behind the mask, the per-channel accumulation is R = v10*(v4+v5),
// G = v6*(v42+v24), B = v7*(v44+v41).
//
// +DELTA_GPU_PSVGPR_AT=<pc> is the tool for walking it. PSVGPR alone reads the
// registers as they stand AT THE EXPORT, and a 2843-instruction shader has
// reused nearly all of them by then -- every term this combine takes is dead
// before its own export, so the plain probe reads something else and says so
// confidently. PSVGPR_AT freezes the three registers the moment the
// instruction at that pc has run, into the same Private slot PSTEX uses, so a
// capture inside a branch still reaches the epilogue. Read the pc off a
// DELTA_GPU_SHDUMP listing.
//
// AND THE MEASUREMENT IS THE HARD PART, not the probe. The light draws add
// into a target the base pass has already written, and this is a CUTSCENE: the
// scene target's own nz swings 122 -> 10328 between frames of one run, which
// is far larger than anything a light contributes. Comparing a probe run
// against a baseline run therefore compares two different pictures, and it
// produced a confident wrong answer twice (a "channel asymmetry" and a
// "red-dominant" reading, both retracted). +DELTA_GPU_PSTEXSCALE now scales
// what PSVGPR exports as well as PSTEX, so a probe can be made to saturate its
// target and be read as present/absent rather than as a small perturbation --
// but the next attempt needs one of:
//   - a STATIC scene to probe (the cutscene never repeats a frame), or
//   - matched frame numbers between probe and baseline runs, or
//   - a readout that cannot be confused with the base pass at all.
// Do not read a single frame's picture and conclude anything.
//
// First reading, and it is a READING not a conclusion:
//   +DELTA_GPU_PROBE_PS=0x20010c4000 +DELTA_GPU_PSVGPR=30
//   +DELTA_GPU_PSVGPR_AT=0xdf8
// exports (v29, v30, v31) = the R, B and G products, captured after all six
// multiplies at 0df3-0df8. On a frame where the base pass wrote almost nothing
// (f650: 31973 of 32459 sampled texels zero, so the target is essentially only
// the probe's output) the 486 texels that ARE set all carry bits above bit 10
// -- values like 00233800, i.e. the middle field populated with R and B at
// zero. That is v30, the blue channel's product, alive while the other two are
// not. 1.5% coverage on one frame is not enough to build on; take it again on
// a frame where the lights cover more, and compare against an unprobed run.
//
// ---------------------------------------------------------------------------
// 59 VERTEX SHADERS WERE BEING THROWN AWAY
// ---------------------------------------------------------------------------
// +DELTA_GPU_SHAUDIT during the CUTSCENE (the old "compute is complete" reading

//   - format-07753, 10946 -> 0. THE PIPELINE CACHE KEY. A pipeline embeds the

//     mrt_uint, the PS input mapping); the key carried the code ADDRESSES and
//     only two of those masks, so a draw could bind a pipeline holding another
//     draw's module while its descriptor set was built from this one's. Every
//     probe that compares against d.recomp is blind to it by construction --

//   - Input-07904, 4554 -> 0. A VS declares an input for every attribute its

//   - Input-08733, 370 -> 0. A 32-bit integer attribute now takes its SFLOAT

//     either order, leaving the dispatch reading the older guest snapshot.

// EARLIER, STILL TRUE

// THE 0.1 FPS WAS AN UNIMPLEMENTED OPCODE. IT_EVENT_WRITE (0x46) with an
// address is an occlusion/statistics query: EVENT_INDEX 1/2/3 sample a counter
// and write it as a 64-bit value whose TOP BIT is the done flag, and the CP
// fans one packet out to one qword PER RENDER BACKEND at a 16-byte stride -- a
// begin packet at `base` fills base + i*16, its end at base+8 fills
// base + i*16 + 8. That is the pair stride the title's poll walks. It emits 289
// a frame and will not render until all sixteen slots carry the bit; it got
// none, so a worker burned 21 half-second timeouts a frame. 0.1 -> 24 fps.
// Gate on EVENT_INDEX (the other forms carry no address and storing through
// their DW2/DW3 crashes) and write a MONOTONIC counter (the slots are
// begin/end pairs read as end - begin).
//
// The poll itself is at eboot+0x1b2f870..0x1b2fa19 and is still the busiest
// thread in the run -- 137 million sched_yields in 47 s. That is not a wedge
// any more, it is waiting for our own command-buffer walk, which costs 37 ms a
// frame. +DELTA_YIELD_CALLER=<period> names it.

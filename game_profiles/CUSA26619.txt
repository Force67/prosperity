// Grand Theft Auto: San Andreas - The Definitive Edition (CUSA26619, PS4)
// UE4 / Gameface, native x86 backend.
//
// BOOTS INTO THE RENDER LOOP (2026-08-01). The title runs UE4 engine init to
// completion, brings up its RHI, and presents: ~356 draws/frame into a 1680x948
// colour target plus 10-24 compute dispatches. Four runs in a row fault-free.
//
// Two things are wrong and neither is a boot problem any more:
//
//  1. ~0.1-0.3 fps. Frame time is nearly all compute. The scene targets are
//     R11G11B10F (dfmt=6 nfmt=7), which the CS path stages at 16 bytes/texel
//     against a 4-byte image, so cs_alias_shape_matches rejects the live image
//     and every dispatch round-trips ~13.6 MB through guest memory -- 9 to 24
//     times a frame, ~95 ms of it. Using the live image needs a real format
//     conversion on the bridge copy, not a relaxed match: a plain
//     vkCmdCopyBufferToImage cannot repack RGBA32F into R11G11B10F. (The
//     descriptor also runs a few rows taller than the image, 948 vs 945, which
//     is just tile alignment and is harmless once the element sizes agree.)
//  2. The presented frame is wrong: frame 0 is a full-screen debug gradient,
//     later frames are solid white. This is NOT a composite/scanout bug --
//     almost nothing is ever drawn. +DELTA_GPU_RTSTAT=1 +DELTA_GPU_RTSTAT_ALL=1
//     +DELTA_GPU_RTSTAT_EVERY=12 at frame 24 says:
//       - the five 1680x948 G-buffer targets (0x2010000000, 0x2010800000,
//         0x2011000000, 0x2011800000, 0x2012000000) each report draws=1 with
//         vs=0 ps=0 -- a clear and nothing else -- and are entirely zero.
//       - 0x2018000000 (256x256) takes 160 draws and is still all zero.
//       - the only targets with content are 0x200ec00000 840x473 (mean=20,
//         half 1.0), 0x200e000000 1680x945 (4135/16538 non-zero) and the two
//         1920x1080 buffers, which are solid white -- that white is what gets
//         presented.
//     So the ~356 draws a frame are not reaching the scene targets. Find where
//     they go before touching the present path; the main colour target
//     (+DELTA_GPU_PRESENT_ADDR=0x2012800000) is confirmed black.
//
// PSN BRING-UP (done). The title calls
// sce::Toolkit::NP::V2::Interface::initialize during engine init and treats any
// failure as LowLevelFatalError "PSN: Failed to initialize the np toolkit".
// Four gates, each only visible once the one before it cleared:
//   1. regmgr op 27 (non-system get-bin) was unimplemented, so libSceNpCommon
//      could not read the 17-byte per-console blob it wants during NpAsm
//      resource-context setup, and the NP stack never started.
//   2. sceSysmoduleLoadModule(0x19) is libSceNet, which we reported absent.
//   3. libSceNpWebApi's initialize reads the LNC app state and refuses to come
//      up unless it is 4 or 5; nothing answered "SceLncService".
//   4. libSceNetCtlForNpToolkit / libSceUserServiceForNpToolkit are second
//      entry-point sets into .sprx files we already HLE, so they read an
//      "initialized" flag the HLE never sets.
// Then libSceAvPlayer: 7 of the 22 NIDs the eboot imports had no HLE override,
// so those ran the real .sprx, which opens each with `mov rdi,[rdi]` on the
// sentinel handle our Init hands out and faults.
//
// The 2026-07-31 note about a UE4 CPU-pool OOM ("Failed to allocate virtual
// address space (Type: CPU, Size: 2140667904)", ~6 GB budget) has NOT recurred
// since; that run reached asset streaming down a different path.
//
// Still unhandled and worth a look if threading looks wrong: umtx op 23
// (SEM2_WAIT) falls through to the "success" arm. Ops 12/13/14 (rwlocks) were
// in the same state and were the cause of the intermittent null-deref crashes.
